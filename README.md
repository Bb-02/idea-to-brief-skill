# 想法成案 · Idea to Brief

**简体中文** | [English](README.en.md)

**把模糊想法，变成有章法的调查。**

你有一个疑问、一个不成熟的点子，或者一个“我觉得这样应该有用”的判断。还不知道该查什么，也说不清怎样的答案才有帮助。

想法成案帮助 AI 接住这些想法：找准目的，检查前提，补上值得调查的角度，选择来源与方法，再交付能支持判断和行动的结果。

**想先理清任务，它帮你成案；想直接得到答案，它帮你调查。**

An Agent Skill for turning rough ideas into actionable research tasks and evidence-based answers.

[看实测](#实测一句话启动并行调查) · [两种用法](#要任务还是要答案) · [安装](#安装) · [验证记录](tests/results.md)

## 实测：一句话启动并行调查

在装有本 Skill 的 ZCode 中，用户用 Qwen 测试。**用户只说了：**

> 我们读书会经常有人报名却不来，我觉得免费活动就是没人珍惜，收点钱应该就好了。帮我调查一下别人遇到这种情况怎么处理，给我一些有依据、能尝试的办法。

根据用户实测反馈，**AI 随后自动启动了三个子 Agent 并发调研**。用户没有手写下面的研究要求；这些提示词由 AI 生成并分发。这里完整展示用户提供的其中两条，保留原文。

<details open>
<summary><strong>子 Agent 1：研究证据、收费效果与替代机制（完整原文）</strong></summary>

> 你是一名调研员，请用 WebSearch 和 WebFetch 做一手资料检索（不要凭记忆编造，所有结论必须附来源 URL 和大致年份）。
>
> 背景：一个志愿者运营的免费读书会经常遇到报名者爽约（no-show），组织者猜测"收费就能解决"。需要检验并扩展这个假设。
>
> 请调研以下问题，重点是**有研究或数据支撑**的结论：
>
> 1. 免费活动 vs 收费活动的爽约率差异：有没有行业统计数据（如 Eventbrite、Meetup、活动管理平台发布的 no-show 数据）？大概数字是多少？
> 2. 行为经济学/心理学解释：沉没成本、付款之痛（pain of paying）、承诺机制（commitment device）——收费减少爽约的机制是什么？有没有经典实验？例如 Volpp 等人在 NEJM 等期刊发表的"押金/小额金钱激励减少预约爽约"实验（milk-deposit study），请核实其设计、数字和结论。
> 3. 收费的副作用：收费是否会吓退报名、改变人群构成？有没有证据？
> 4. 不收费但同样有效的机制：预约确认提醒（尤其是 SMS/短信提醒在医疗预约领域的效果研究，量化降低爽约率的数据）、可退还押金（deposit 到场即退）、公开承诺、候补名单（waitlist）、社会规范/同伴压力、签到制、习惯性缺席惩罚（如三次取消规则）——每一项找有没有实证或可靠实践来源。
> 5. 有没有"押金可退"优于"直接收费"的证据？
>
> 要求：
>
> - 用中英双语关键词搜索（如 "no-show rate free vs paid events", "commitment device reduce no-show", "appointment reminder SMS reduce no-show percentage", "金钱激励 爽约 预约"）。
> - 每条结论标注：来源标题、URL、年份、是同行评议研究/行业报告/从业者经验（分层）。
> - 明确区分"证据支持""证据相互矛盾""只是说法"。
> - 找不到的就直说找不到，不要编造数字。
>
> 输出：中文调研报告，结构化列出发现，每条附来源。

</details>

<details>
<summary><strong>子 Agent 2：社群实践、平台机制与反面经验（完整原文）</strong></summary>

> 你是一名调研员，请用 WebSearch 和 WebFetch 检索**真实社群组织者的实践经验**（不要凭记忆编造，结论附来源 URL）。
>
> 背景：一个免费读书会（几十人规模，志愿者运营，线下或线上线下混合）报名者经常爽约。我们想知道其他俱乐部/社群/Meetup 组织者实际用什么办法治理"报名不来"，以及效果如何。
>
> 请调研：
>
> 1. Reddit（r/Meetup、r/community、r/nonprofit 等）、Meetup 社区论坛、活动运营博客里，组织者讨论"no-show / people don't show up"的帖子：他们总结了哪些有效做法？哪些被证明无效？特别注意一手经验帖（"我们试过 X，结果是……"）。
> 2. Meetup / Eventbrite / Luma / 活动行 / 互动吧 等平台自带的机制：RSVP 管理、押金（deposit）、候补名单、自动提醒、no-show 标记/取消资格功能——各自怎么用、平台文档怎么说。
> 3. 具体做法清单及其在实践中的反馈：
>    - 收取象征性费用（哪怕 1-5 元）或到场退还的押金
>    - 活动前 24 小时要求"确认参加"，不确认视为取消、释放名额给候补
>    - 三次爽约拉黑/限制报名规则
>    - 报名截止 + 名额限制 + 候补名单
>    - 微信群接龙/报名接龙、签到表、拍照留档
>    - 小组化（固定班底、互相认识）来提高出席动力
>    - 收费模式的社群（如付费读书会）实际出席率如何，免费转付费的组织者怎么说
> 4. 有没有反面经验：收费/押金导致报名骤降、气氛变差、志愿者难执行的案例？
>
> 搜索建议：用英文如 "meetup organizer how to reduce no-shows reddit", "eventbrite deposit no show", "how to stop people from flaking on your meetup", 中文如 "读书会 报名 爽约 押金", "活动 鸽子 怎么办 社群"。
>
> 要求：每条做法注明出处和来源类型（平台官方文档 / 从业者一手帖 / 运营文章），有数字的抄数字，找不到量化数据的就说明只是经验谈。不要编造。
>
> 输出：中文结构化报告：有效做法清单（按证据强度排序）、无效或有风险的做法、来源列表。

</details>

一句日常表达，展开出了**前提检验、替代方案、来源选择、具体检索词、证据要求和交付形式**。这正是想法成案希望帮助 AI 做好的研究组织工作。

<sub>案例由用户提供并授权公开，展示的是任务分发原文，不是最终调查结论。原文中的补充背景与具体研究线索仍需核实；三个并发 Agent 是这次运行的选择，不是 Skill 的固定要求。工具名称和可用能力取决于宿主环境。</sub>

## 它为 AI 补上什么

- **把直觉变成可调查的问题。** 分清你想达成的目标、提出的办法和未经验证的解释，让证据有机会修正最初的判断。
- **补上你可能没想到的角度。** 比较替代办法、隐藏成本、适用条件和关键风险；每一项补充都应当服务于你的目的。
- **让来源各司其职。** 查功能看官方资料，查效果找相应研究，查实际操作找一手经历；说清资料能支持什么、还不能证明什么。
- **把研究落到下一步。** 交付可执行的任务，或有依据的比较与建议，让你知道接下来可以做什么。

你可以用日常语言提问，不必先掌握领域术语，也不必自己写一套复杂的研究提示词。

## 要任务，还是要答案？

同一套研究方法，两种交付。

|  | 任务设计 | 直接研究 |
| --- | --- | --- |
| 适合你想…… | 理清想法、编写提示词、把任务交给另一个 AI | 现在就搜索、调查、比较，拿到结论 |
| AI 会做什么 | 整理目标、范围、问题、方法和交付要求 | 内部组织调查，使用可用工具检索、筛选和核实 |
| 你得到什么 | 完整、可复制、可独立使用的任务说明 | 发现、来源、适用条件与必要的行动建议 |
| 到哪里结束 | 默认交付任务说明后结束 | 完成请求范围内的调查，不强制先交任务书 |

例如，同样关心学习方法：

**先帮我成案**

> 跟着教程能做出来，换个题目就不会了。我想弄明白怎么调整学习方法，帮我整理成能直接交给另一个 AI 的调查任务。

**直接帮我调查**

> 跟着教程能做出来，换个题目就不会了。请查查相关研究，告诉我可以怎么调整学习方法，并说明建议的依据。

信息足够就开始完成所需交付；只有缺失信息会实质改变任务时才询问。明确指定提示词、简短答案或其他形式时，尊重你的选择。

任务说明交付后，你可以继续说“太复杂了，给我简化后的完整版本”，也可以说“现在按这份任务开始调查”。对草案说“不错”，不会自动启动后续执行。

## 该展开时展开，该收住时收住

| 你要做的事 | 合适的投入 |
| --- | --- |
| 找一些作品、工具或灵感 | 覆盖不同方向，基本核实、筛选、去重，给简短清单与来源 |
| 调查一种做法、比较几条路线 | 查具体证据、适用条件与成本，形成能开始行动的建议 |
| 深入研究一个复杂问题 | 按需安排独立探索、重要主张验证、反例与阶段汇总 |

题目广，可以查得浅；问题窄，也可能值得深挖。Token 多、时间充足，不代表必须写更多报告或用完资源。

复杂调查在宿主允许且确有价值时可以并行。**多 Agent 是可选手段**，没有固定角色或并发数量；关键仍是问题拆得有用、证据查得可靠、结果能够汇总。

你举的例子只是线索，除非你明确把它设为边界。你说“那个只是举例”“取消旧限制”“这次简单一点”，任务就应随最新要求调整。AI 补充的假设，也应与你已经确定的要求分开。

## 安装

正式版：**v1.0.0** · [查看版本](https://github.com/Bb-02/idea-to-brief-skill/tree/v1.0.0) · [下载源码 ZIP](https://github.com/Bb-02/idea-to-brief-skill/archive/refs/tags/v1.0.0.zip)

使用 [Skills CLI](https://github.com/vercel-labs/skills) 从 GitHub 安装：

```bash
npx skills add Bb-02/idea-to-brief-skill --skill idea-to-brief
```

例如，指定 Codex 并复制安装：

```bash
npx skills add Bb-02/idea-to-brief-skill --skill idea-to-brief --agent codex --copy
```

默认项目安装；需要全局安装时添加 `--global`。也可以把整个 `skills/idea-to-brief/` 复制到客户端指定的 Skill 目录，保留参考文件、元数据和许可证。复制安装后，更新源文件不会自动更新另一份副本。

如果已经克隆仓库，也可以在仓库目录运行 `npx skills add . --skill idea-to-brief`。

## 开始使用

在支持显式调用的环境中，可以这样开始：

```text
$idea-to-brief 我想研究个人开发者怎样推广自己的作品，但不知道该看哪些渠道。帮我整理成一个实用的调查任务。
```

或者直接要结果：

```text
$idea-to-brief 请调查个人开发者怎样推广自己的作品，给我有案例依据的渠道比较和起步建议，一个人能做得过来。
```

自动选择取决于模型与客户端。这个 Skill 适合需要组织范围、来源、比较标准或证据的任务；普通事实问答、单项查询、日常安排和常规开发任务保持原有方式。只说“以后可能用得上”，也不意味着必须展开完整研究。

中文输出按需要使用“任务说明”“研究任务”“提示词”等自然说法。短任务可以直接在对话中完成，无需统一长模板或额外文件。

## 方法之外，还需要什么

实际联网、文件访问、运行实验和子 Agent 能力由宿主提供。想法成案指导 AI 怎样组织工作；结果质量仍取决于模型、工具、可获得的资料，以及执行时是否认真核验。

写任务说明时，必要的前提查证应保持适度。直接研究时，结论应能追溯到实际查阅的来源；工具不可用、资料不足或查不到的部分应如实说明。临时失败有限重试，持续失败保留缺口。研究请求也不包含替你发帖、部署或修改外部系统的授权。

## 如何验证

本地验证已覆盖同题的“生成提示词 / 实际联网调查”对照、已有资料比较、多轮模式切换、能力不足和简单问答。具体设置、观察与未测部分见 [验证记录](tests/results.md)。

你也可以用 [测试案例](tests/cases.md) 在自己的环境中试用。技能是否被加载、是否自动选中、交付是否合适、研究结果是否可靠，分别记录；一次成功调用不代表所有问题和模型都表现一致。
